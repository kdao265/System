## 3. Proposed delivery batches and decision points

**Batch A — high-risk fail-closed** (QA-10, QA-23, QA-12): test only in disposable PostgreSQL/Auth/PostgREST; record timezone provenance and owner-authenticated edge cases. If SQL/TS mismatch, privilege/privacy violation, nonrepeatable tzdb result or unexplained SQLSTATE occurs, **stop**; preserve failing inputs/logs and request a separately authorized **narrow** business-SQL fix.

**Batch B — domain parity** (QA-06, QA-08, QA-11, QA-19, QA-20): run one declared finite fixture table per field/action, with expected accept/reject and exact before/after history and receipts. Avoid loosely asserted `some error` as proof of canonical contract. If Batch A is blocked, do not mask it behind unrelated green tests.

**Batch C — snapshot audit** (QA-32): reuse fixtures and traces from A/B as well as all existing L1-07..11 coverage; explicitly enumerate previously missing mutation classes and cross-domain expected invariants. No unbounded cross-product nor repeated CI without a coverage target.

**Verification for each completed batch:** source-level preflight, local test syntax/type checks, fixture PostgreSQL+Auth+PostgREST runner, Quest Creation CI and Playwright E2E **on the exact new PR HEAD**. Log actual run URL/SHA, any skips and exact assertion counts. A browser E2E PASS for existing pages cannot close QA-09 until AO UI exists.

**Evidence gate per row:** only switch a specific QA to PASS after comparing its full scenario wording with executable assertions and CI logs; otherwise remain PARTIAL with a concrete reason. Append dated evidence to `review/qa-matrix.md`. Do not mark test implementation as runtime PASS.
